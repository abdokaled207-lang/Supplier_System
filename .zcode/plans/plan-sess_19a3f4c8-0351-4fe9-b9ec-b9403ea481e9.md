# Refactor Plan — ROTI CHANI KING (Backend-first, staged)

## Reality check vs. the prompt
The prompt's premises partly don't match this codebase, so the plan targets the actual code:
- Frontend is **React + Vite + TanStack Query**, not Next.js (no `next/image`; image optimization = `loading="lazy"`/`decoding="async"` on `ProductImage`).
- There is **no image upload** — `imageUrl` is a plain URL field, so "compress uploaded images" doesn't apply.
- **Most list pages already paginate** server-side (Orders, Customers, Products, StockReceipts, Activity) via `utils/pagination.ts`.
- API access is already centralized (`frontend/src/api/client.ts`, env-driven `VITE_API_URL`); zero `any` and zero stray `console.log` on both sides; error handling is already centralized (`middleware/error.ts` + `InlineError`).
- The real gaps: only the **orders** module uses the domain/adapter pattern — all other modules call Prisma directly in routes; several duplicated frontend helpers; Dashboard fetches the whole orders table; missing insensitive search; `Invoice.tsx`/`Activity.tsx` have local date formatters and ~14 ad-hoc `RM` money interpolations.

## Stage 0 — Git checkpoint
Commit the current uncommitted manual edits as-is on `manual-edits-delete-daily-area` so every refactor stage is a clean, revertable commit of its own.

## Stage 1 — Backend service layer + centralized error handling (module by module)
Follow the proven orders pattern (`domain/fulfillment.ts` + `db/orderAdapter.ts` seam). For each module, move Prisma access and multi-step transactional logic out of route handlers into a per-module service in `src/modules/<name>/<name>.service.ts` (thin routes keep: parse → zod validate → call service → respond). Order of work, one commit each:
1. **payments** — inline transaction/guards → service (overpayment guard already covered by `domain/orderMoney.ts`; don't alter its math).
2. **stockReceipts** — inline transactional receipt logic → service.
3. **customers**, **products** — CRUD/search/list reads → services.
4. **search**, **activityLogs**, **auth** — small services; keep the fire-and-forget activity-log write as-is.
- Error handling is already centralized (`middleware/error.ts`, `utils/http.ts`); extend it only if services surface new error shapes. No behavior change to status codes/codes.
- After each module: `npm run typecheck && npm run lint && npm test` (tests mock `src/db/prisma`; update mocks where a service layer shifts import paths).

## Stage 2 — Prisma performance review
1. **N+1**: `orders.routes.ts` PUT edit loops `getProduct` per item → batch fetch products in one query inside the fulfillment flow (keeps the `OrderAdapter` seam; extend its interface). `decrementStock`'s per-item sequential updates stay (they're the atomic race guard inside one transaction — correctness over micro-perf).
2. **Search**: add `mode: "insensitive"` where the DB supports it (MySQL does) for substring search on customers/products/orders — user-visible improvement in match behavior is accepted as a bug-level fix, not a feature change.
3. **Indexes**: add a Prisma migration with `@@index` on the hot filter columns (`Orders.orderDate` already indexed; review `Payments.orderId`, `OrderItems.orderId` — already present; add any genuinely missing ones found during review). Migration via `npm run db:dev`; **no data-model changes**, indexes only.
4. **Dashboard stats endpoint**: new `GET /reports/dashboard` (service in `domain/reports.ts`) computing today/period totals and customer balances in SQL aggregation; Dashboard.tsx switches to it, dropping the full-table fetch. UI numbers identical.
5. Payments list: scope the unpaginated `GET /payments` to sensible pagination consistent with other list endpoints (verify no page depends on full-list behavior first).

## Stage 3 — Frontend cleanup
1. **Shared hooks**: `src/api/hooks.ts` with `useProducts()`, `useCustomers()`, etc., replacing the copy-pasted `useQuery` blocks (Orders.tsx:55–56, EditOrder.tsx:30–31, Dashboard.tsx:34).
2. **Shared formatters**: one `formatMoney` in `src/utils/` replacing ~14 ad-hoc `RM` interpolations and stray `toFixed(2)`; delete `Invoice.tsx`'s local `formatDate` and `Activity.tsx`'s inline `toLocaleString` in favor of `utils/datetime.ts`.
3. **Re-renders**: `useMemo` only where genuinely needed (Dashboard aggregation now moves server-side anyway); no blanket memoization.
4. **Images**: `loading="lazy" decoding="async"` on `ProductImage.tsx`.
5. **Types**: keep the single `src/api/types.ts` as the mirror of backend entities (money as `string`), align with any response-shape changes from Stages 1–2.
6. No toast-system redesign or CSS split (that would change user-facing behavior/scope); leave the existing `InlineError`/`ConfirmDialog` patterns.

## Stage 4 — Env/secrets final review
Verify all config stays env-driven (`backend/src/config/env.ts` zod-validated, `frontend/.env*` for `VITE_API_URL`); check `.env.example` matches reality; confirm nothing hardcoded leaked in during the refactor. Frontend has no secrets.

## Verification & constraints
- Every stage ends with backend `typecheck + lint + test` (and frontend `typecheck + lint + build + test` in Stage 3), a commit, and a written summary of changes + impact.
- **Baki Tertunggak** (outstanding balance: `domain/orderMoney.ts` `orderTotals`/`paymentStatusFor`/`decorateOrder` and the customer-balance aggregation): verify correctness only; if any change proves necessary, it gets reviewed by spec-guardian before the stage is considered done.
- No Expo/mobile-app-related files are read or touched.
- No user-facing behavior change except: case-insensitive search matches, and Dashboard's faster load (same numbers).
